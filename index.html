DOCKER FOUNDATIONS

01. Docker fundamentals

Docker packages an application and its dependencies into an image, then runs that image as a container.

What is Docker?

Docker is a platform for packaging and running applications in containers. A container bundles an application with the files and dependencies it needs, so it can run more consistently across a developer's laptop, a test environment, and a server.

Think of the application as a meal: the source code is the recipe, the image is the prepared package, and a container is one running instance made from that package.

ApplicationCode and files
ImagePackaged template
ContainerRunning instance

Why use Docker?

  • Consistency: package the app and dependencies together to reduce “it works on my machine” problems.
  • Portability: run the same image on compatible Docker environments.
  • Isolation: keep application processes and files separated from other containers.
  • Repeatability: build a new container from a versioned image whenever you need another instance.
  • DevOps workflow: build, test, publish, deploy, and roll back using known image versions.
Beginner tip: Docker does not magically make an application secure or identical on every operating system. Use trusted images, keep dependencies updated, and configure ports and secrets carefully.

Try it: download an image and start two containers

Run each command in your terminal. The first command downloads the Nginx image. The next two create two separate containers from that same image. The final command lists running containers.

docker pull nginx:alpine
docker run -d --name web1 nginx:alpine
docker run -d --name web2 nginx:alpine
docker ps

What to notice: web1 and web2 are separate containers, but both were created from nginx:alpine. These examples do not publish a host port yet; port mapping is covered below.

Docker image layers — a visual example

Images are composed from reusable filesystem layers. The actual layers depend on the image and the instructions used to build it.

Layer 4Application filesHTML · CSS · Python code
Layer 3DependenciesLibraries and packages
Layer 2RuntimeTools needed to run the app
Layer 1Base imageStarting filesystem and utilities

Illustrative stack — a real image can contain a different number and arrangement of layers.

Example Dockerfile

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
InstructionMeaning
FROMSelects the starting/base image.
WORKDIRSets the working directory inside the image.
COPY requirements.txt .Copies the dependency list into the working directory.
RUNRuns a command during the image build; installing packages changes the filesystem.
COPY . .Copies files from the build context into the image, except files excluded by .dockerignore.
CMDSets the default command to run when a container starts; it is image configuration, not a filesystem layer.

Why are image layers useful?

  • Reuse: multiple images can share common layers.
  • Caching: Docker can reuse unchanged build steps when rebuilding an image.
  • Efficiency: Docker generally downloads only layers it does not already have locally.
  • Smaller updates: if dependencies stay the same but app.py changes, Docker may reuse the dependency-installation layer when the Dockerfile is ordered appropriately.

Inspect image configuration and layer-related metadata with:

docker image inspect nginx:alpine
docker history nginx:alpine

docker image inspect shows detailed image configuration and metadata. docker history displays image build history, including layer sizes and associated instructions where available.

Port mapping: connect your computer to a container

A container can listen on a port internally, but your computer needs a published host port to access that service from the host. For the Nginx example, the web server listens on container port 80.

Your computerHost port 8080http://localhost:8080
Docker port mapping8080 → 80
Nginx containerContainer port 80Nginx receives HTTP requests

Understand the -p option

docker run -d -p 8080:80 --name mynginx nginx:alpine

The format is -p HOST_PORT:CONTAINER_PORT.

PartMeaning
-pPublishes a container port on the host.
8080The port on your computer (host).
80The port inside the container.
--name mynginxGives the container a readable name.
-dRuns the container in the background.

When you open http://localhost:8080, Docker forwards the connection from host port 8080 to container port 80. Port 80 inside the container does not automatically mean your computer is listening on port 80.

Practise port mapping step by step

  1. Download the Nginx image:
    docker pull nginx:alpine
  2. Start a container and publish port 8080:
    docker run -d -p 8080:80 --name mynginx nginx:alpine
  3. Check that it is running:
    docker ps

    Look for a port entry similar to 0.0.0.0:8080->80/tcp or an equivalent host binding.

  4. Open the site: visit http://localhost:8080. You should see the Nginx welcome page.

Try other host ports

MappingBrowser URL
-p 8080:80http://localhost:8080
-p 3000:80http://localhost:3000
-p 9000:80http://localhost:9000

These are alternative examples: each mapping sends a different host port to container port 80. If host port 8080 is already occupied, use another available port. Do not start multiple containers with the same host port at the same time unless you intentionally configure a different setup.

Stop and remove the practice container when you finish:

docker stop mynginx
docker rm mynginx
Quick revision
  • Docker image: a template used to create containers.
  • Image layers: reusable filesystem changes that can improve caching and storage efficiency.
  • Port mapping: makes a container service accessible through a port on your host computer.

Step 7 — Understand containers versus virtual machines

Step 7 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
  • Virtual machines normally run a guest operating system on virtualised hardware.
  • Containers share the host kernel and isolate processes using operating-system features.
  • Containers are usually quick to start and lightweight, but they are not a replacement for every VM use case.
  • Containers still require security controls and should not be treated as perfectly isolated by default.

DATA AND CONNECTIVITY

04. Volumes and networks

Step 14 — Understand persistent storage

Step 14 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.

A container's writable layer belongs to that container. If the container is removed, data stored only in that layer can be lost.

  • Named volume: Docker-managed persistent storage, often useful for database data.
  • Bind mount: maps a host directory/file into a container, useful for local development.
  • tmpfs: temporary in-memory storage on supported platforms.

Step 15 — Create and test a volume

Step 15 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
docker volume create mevi-data
docker volume ls
docker volume inspect mevi-data
docker run --rm -v mevi-data:/data alpine sh -c "echo 'persistent note' > /data/note.txt"
docker run --rm -v mevi-data:/data alpine cat /data/note.txt

The first temporary container writes to the volume; the second reads the same file. This shows that the data can outlive both containers.

Step 16 — Create a user-defined network

Step 16 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
docker network create mevi-net
docker network ls
docker run -d --name web-net --network mevi-net nginx:alpine
docker network inspect mevi-net
docker rm -f web-net
docker network rm mevi-net

Containers on a user-defined network can usually reach one another by container/service name. Publish only ports that need to be reached from outside the Docker network.

In -p 127.0.0.1:5000:8000, the host-side service is bound to loopback and intended for local access. Binding to all host interfaces can expose the service to other devices, depending on firewall and network settings.

08. Python Flask tutorial

Flask maps incoming HTTP requests to Python functions called route handlers. A handler can return HTML, JSON, text or a redirect.

Step 28 — Write app.py

Step 28 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
from flask import Flask, jsonify, render_template

app = Flask(__name__)

@app.get("/")
def home():
    return render_template("index.html")

@app.get("/health")
def health():
    return jsonify(status="ok", application="Mevi Flask Demo")

@app.get("/api/greet/<name>")
def greet(name):
    return jsonify(message=f"Hello, {name}!")

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=5000, debug=True)
  1. Flask(__name__) creates the application and helps Flask locate resources.
  2. @app.get("/") registers a handler for HTTP GET requests to the root path.
  3. render_template loads and renders templates/index.html.
  4. jsonify returns a JSON response, useful for API endpoints and health checks.
  5. <name> is a dynamic route parameter passed to the function.
  6. The final block starts Flask's development server when this file is run directly. Debug mode is for local development only.

Step 36 — Understand the container host binding

Step 36 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.

The local development example binds to 127.0.0.1 intentionally. Inside a container, a service that should receive forwarded traffic must listen on the container interface, commonly 0.0.0.0. The Dockerfile below runs Gunicorn on 0.0.0.0:8000.

Step 37 — Create the Dockerfile

Step 37 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
COPY templates/ ./templates/
COPY static/ ./static/

RUN useradd --create-home --shell /usr/sbin/nologin appuser
USER appuser

EXPOSE 8000

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "app:app"]

Instruction explanations:

  1. FROM selects a slim Python base image.
  2. PYTHONDONTWRITEBYTECODE prevents Python bytecode files from being written.
  3. PYTHONUNBUFFERED helps logs appear promptly.
  4. WORKDIR sets the working directory inside the image.
  5. COPY requirements.txt copies dependency definitions first, allowing Docker to reuse the install layer when app code changes.
  6. RUN pip install installs packages while building the image.
  7. The next COPY instructions add the Python module, templates and static assets.
  8. USER appuser runs the application as a non-root user.
  9. EXPOSE 8000 documents the container port; it does not publish it to the host.
  10. CMD starts Gunicorn. app:app means module app.py and Flask object named app.

Step 47 — Optimise images

Step 47 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
  • Choose a supported base image that meets compatibility needs.

Step 48 — Security checklist

Step 48 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
  • Run as a non-root user wherever practical.
  • Use trusted base images and review their provenance.
  • Scan dependencies and images for known vulnerabilities.
  • Do not publish database/admin ports by default.
  • Use HTTPS at the appropriate ingress or reverse-proxy layer for public deployments.
  • Never use Flask debug mode or the development server in production.
  • Limit registry credentials and deployment-token permissions.
  • Monitor CPU, memory, disk use, request failures and application logs.

13. Troubleshooting guide

Start Docker Desktop on Windows/macOS or the Docker Engine service on Linux. Then run docker info. Linux service commands vary by distribution.

Another process/container uses that host port. Check docker ps, stop the conflicting container if appropriate, or use a different host port such as 127.0.0.1:5001:8000.

Run docker ps -a and docker logs CONTAINER. Containers stop when their main process exits. Check the command, imports, dependencies and configuration.

Check container status and logs, verify the app listens on the expected container port, and confirm host-to-container port mapping. Binding only to 127.0.0.1 inside the container may prevent forwarded traffic reaching it.

Check requirements.txt, rebuild after dependency changes, and confirm the Dockerfile installs from the intended file. Locally, activate the correct virtual environment.

Flask expects templates in a folder named templates by default. Check spelling and case, and ensure the Dockerfile copies the directory into the image.

A normal image contains a snapshot of files. Rebuild the image and recreate the container. A bind mount can be used for local development if configured intentionally.

Run git status. The file may not have changed, may already be committed, or may be ignored. Use git check-ignore -v path/to/file to identify the matching ignore rule.

Step 51 — Follow a repeatable debugging sequence

Step 51 — do this now: Follow the instructions immediately below this heading. Run the commands in the order shown, or create/edit the named file if the instructions give code. Then check the result before continuing.
  1. Reproduce the issue and note the exact command or URL.
  2. Check status using docker ps -a.
  3. Read logs with docker logs or docker compose logs.
  4. Inspect ports, environment and mounts using docker inspect.
  5. Change one thing at a time, rebuild/restart and retest.
  6. Record the root cause and solution in README or an issue tracker.
